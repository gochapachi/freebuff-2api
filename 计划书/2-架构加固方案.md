## 2.1 双桶并发信号量（README 宣称已实现的落地方案）

### 现状问题
README 与 README_en 都声称「双桶并发信号量—逆向自上游：免费 `{槽:1, 普通:3}`、订阅 `{槽:3, 普通:8}`」，但 `rg "Semaphore|semaphore|slot" src/` **零命中**，api.rs 转发路径（`handle_chat_completions` / `handle_claude_messages` / `web_bridge_openai`）没有任何并发 GCD。多账号高并发时可能撞上游并发墙（429 / waiting_room 加重 / 风控指纹）。

### 方案设计（最小改动、不重构）

新模块 `src/semaphore.rs`：

```rust
pub struct TieredSemaphore {
    free: Arc<tokio::sync::Semaphore>,    // 免费层 {slot:1, multi:3}
    subscriber: Arc<tokio::sync::Semaphore>, // 订阅层 {slot:3, multi:8}
}

impl TieredSemaphore {
    pub async fn acquire(&self, is_subscriber: bool) -> Result<TierGuard, AcquireError>;
    // TierGuard 持 permit，Drop 时自动归还（RAII，杜绝泄漏）
}
```

- **判定上下**：请求进来先看账号池 `AccountEntry` 是否含订阅信息（session `access_tier` 或 `unique_subscription`）。无订阅信息默认走 free 桶（保守）。
- **接入点**：`handle_chat_completions`（Bearer 主链路）与 `handle_claude_messages` 与 `web_bridge_openai` 三处，在 **首字节写出前** acquire；流式完成后（后台收尾任务）Drop 归还。
- **超时**：`try_acquire` + 2s 超时，超时返回 429 级错误（`waiting_room` 语义对齐），不无限排队。
- **多账号并发**：信号量是**网关全局级**（所有账号共享），因为上游并发墙是按**网关 IP/账号**维度算的，不是按单会话。
- 配置：`config.rs` 增 `concurrency_free_slots / concurrency_free_multi / concurrency_sub_slots / concurrency_sub_multi`（默认 1/3/3/8），面板「原理」页文档同步。
- 环境变量：`CONCURRENCY_*` 四组，沿用 `parse_duration_sec` 同一套 env 覆盖模式。

### 验收标准
- [ ] 单测：free vs subscriber 两桶互不干扰；permit 耗尽时 acquire 阻塞/超时正确；Drop 归还后可再次 acquire；guard 无泄漏（固定次数循环后信号量计数复原）。
- [ ] 集成测试：Mock 上游慢响应下并发 50 个请求，同时通过数 ≤ 桶容量。
- [ ] 面板「原理」页与 README 描述与实际行为一致。

## 2.2 Claude 路径（/v1/messages）重试 + 记账 + 记忆（当前缺失）

### 现状问题（代码级核验）
`handle_claude_messages`（api.rs:2271）与 OpenAI 路径相比**三缺**：
1. **无重试**：`ensure_session` 的错误被 `let _ = ...` 吞掉；上游 5xx / waiting_room 直接 502，不换号。
2. **无用量记账**：成功路径直接 `Json(claude_resp)` 返回，没有 `usage_db.record_ex` / `telemetry.record`；流式路径有 telemetry 但无 usage 落库。
3. **无记忆 observe**：`memory.observe` 只在 OpenAI 路径调用，Claude 用户的偏好/纠正学习不到。

### 方案设计
- **重试**：把 OpenAI 路径的「请求级重试循环」（`for attempt in 0..max_attempts` + 账号重选 + 熔断/冷却 + waiting_room 处理）**提取为公共异步 helper**（放 api.rs 或新建 `src/request_pipeline.rs`），OpenAI 与 Claude 两路径共用；Claude 路径错误响应体转为 Claude 错误形状（已有 `openai_error_to_claude` 可复用的部分）。
- **记账**：非流式 Claude 响应解析出 `prompt_tokens / completion_tokens`（`extract_usage` 复用），补 `usage_db.record_ex` + `telemetry.record`（含 `client_ip`）。流式路径已记账遥测但缺 usage 落库，一并补。
- **记忆**：成功路径补 `memory.observe(&resolved, effort_downgraded.as_deref(), &mem_query, None)`（沿用运行时开关）。

### 验收标准
- [ ] Claude 非流式请求在面板用量/请求详情可见。
- [ ] Claude 排队（waiting_room）返回 503 + 可读消息而非裸 502。
- [ ] Claude 5xx 自动换号重试（Mock 上游验证调用次数）。
- [ ] 记忆开关开启时，Claude 对话触发 observe（用例数增加）。

## 2.4 不做的（避免范围蔓延）

- ❌ 不重构 api.rs 巨型函数（4.2K 行保持原样，仅在内部接线）
- ❌ 不引入新的重量级框架/依赖（保持 `Cargo.toml` 依赖面不变）——信号量用 tokio 自带 `Semaphore`
- ❌ 不改动 upstream 协议层（`upstream.rs` / `web_protocol.rs` 的请求头与协议细节是逆向成果，不碰）
- ❌ 不在本轮做 SSE 攒批提交（workflow_status 已评估收益/风险比不足，保留 backlog）
